# Execution-timing comparison

## Shared intended sequence

1. Bar N completes.
2. Only closes through bar N are visible to the moving-average signal.
3. A long-or-flat target is produced after readiness.
4. Risk reviews the target.
5. The earliest eligible order execution is bar N+1 market open.
6. A target produced from the final completed bar is canceled/expired and never
   receives a fabricated fill.

## Local oracle

The local input row labels a completed UTC bar. A pending target fills exactly
at the next input row's `open`, after configured adverse slippage. All opens are
validated before the run. There are no partial fills, exchange calendars, or
cash settlement delays. Quantity and money use configured decimal-place
rounding over Python floats.

## Validated LEAN cloud baseline

The completed SPY cloud baseline follows the US equity exchange calendar and
corporate-action normalization. Its execution component submits a
market-on-open order only after a completed daily slice. Those successful runs
validated cloud wiring, not identical-data timing.

## Dedicated identical-data path

`ParityFixtureV1` instead parses the exact eight LF-terminated rows from
`tests/fixtures/parity/v1/synthetic_weekdays.csv`, SHA-256
`a68bcf7fc30d2593b32e5a98852c4f8e0190ed99865640485b344515d9f1f78a`.
One custom-data parser serves both the default local file and the explicitly
selected fixed Object Store key. Transport selection cannot change timestamps,
bars, signals, fills, costs, risk, accounting, or rounding.

When custom row N becomes visible, only closes through N may update the
trailing windows. Any resulting target is pending until row N+1 arrives, whose
`open` is the sole reference price for the deterministic adverse-slippage fill.
The order intent, risk decision, and fill are labelled with the N+1 timestamp
and `execution_phase=open`; the N+1 close is not visible to the signal that
created them. No code may inspect a future custom-data row.

A target generated by the eighth and final row records an unfilled pending
signal without creating an intent or fill. Missing content, the wrong fixture
hash, a malformed row, or an unavailable selected transport fails before this
sequence can begin.

dedicated input, timing, observation, and comparison boundaries are prepared.
No local or cloud LEAN engine has executed `ParityFixtureV1`, and no Object Store

## Identical-fixture comparison rules

| Area | Rule |
|---|---|
| Fixture and calendar | Exact same eight UTC-labelled rows and normalized-bars hash |
| Visible history | Exact timestamps and trailing-only readiness |
| Signals, intents, fills | Exact timing, execution phase, direction, and count |
| Quantity | Exact; the v1 quantity tolerance is `0` |
| Price | Absolute tolerance `0.00000001` |
| Money | Absolute tolerance `0.01` |
| Derived ratios | Absolute tolerance `0.0000001` |
| Risk and final bar | Exact reasons, halt state, and pending-signal status |

The one-cent money and ratio tolerances cover only the named fee-hook precision
difference. The identical fixture removes exchange-calendar, corporate-action,
and remote-market-data differences from this comparison. Any unexplained
signal, direction, timing, position, or accounting divergence fails.
